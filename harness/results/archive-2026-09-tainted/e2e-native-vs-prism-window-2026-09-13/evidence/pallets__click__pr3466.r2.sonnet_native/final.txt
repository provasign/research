## Summary

The zsh (and other shell) completion source script is generated by `shell_complete()` in `src/click/shell_completion.py` and written via `click.echo()`. On Windows, `echo()` writes to the text-mode stdout stream, which performs newline translation (`\n` → `\r\n`). The generated script embeds multi-line constructs like `if [[ ... ]]; then ... elif ... fi`; when each line ends up with a trailing `\r`, keywords like `then`/`elif` become `then\r`/`elif\r`, which zsh (particularly under msys2/Git-for-Windows) fails to parse, producing `parse error near 'elif'`.

I reproduced this exactly by converting the source script's `\n` to `\r\n` and confirmed `zsh -n` fails with the reported error.

**Fix** (`src/click/shell_completion.py`): encode the generated source script to `bytes` before passing to `echo()`. Click's `echo()` already special-cases bytes/bytearray by writing directly to the underlying binary stream, bypassing text-mode newline translation — so the script is written verbatim with `\n` only, regardless of platform.
